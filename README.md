# Week 04: Authentication & RBAC with AI Co-Piloting

A small full-stack app that demonstrates authentication (who are you?) and role-based access control (what are you allowed to do?). The code was generated by an AI assistant, then audited, tested, and patched by me.

## Author
- Eric Cashman

## Project Overview

- Users can **register**, **log in**, and **log out**.
- There are two roles: `User` and `Admin`. Anyone who registers becomes a `User`. An Admin is created only by a server-side seed script.
- Three endpoints show the three access levels:

| Endpoint | Access | Result for wrong access |
|---|---|---|
| `GET /api/public` | Anyone | n/a |
| `GET /api/profile` | Any logged-in user | `401` if logged out |
| `GET /api/admin/users` | Admin only | `401` if logged out, `403` if logged in as User |

## Tech Stack

- **Node.js 22+** and **Express 5**
- **SQLite** via `better-sqlite3` (all queries are parameterized)
- **bcrypt** (cost factor 12) for password hashing
- **JWT** (`jsonwebtoken`) in an `httpOnly`, `SameSite=Strict` cookie, 1 hour expiry
- **helmet** for security headers, **express-rate-limit** for login throttling
- **dotenv** for secrets
- Plain HTML and JavaScript frontend (no framework)

## Setup Guide

1. **Install Node.js 22 or newer.**
2. **Clone and install:**
   ```
   git clone https://github.com/Eric-Cashman/week04-auth-rbac.git
   cd week04-auth-rbac
   npm install
   npm install better-sqlite3@12
   ```
   (`better-sqlite3@12` is pinned because newer versions need Visual Studio to compile on Windows.)
3. **Create your `.env` file** by copying the example:
   ```
   copy .env.example .env
   ```
   Then edit `.env`:
   ```
   PORT=3000
   NODE_ENV=development
   JWT_SECRET=<a random string of at least 32 characters>
   ADMIN_USERNAME=admin
   ADMIN_PASSWORD=<at least 12 characters>
   ```
   The server refuses to start if `JWT_SECRET` is missing or shorter than 32 characters. `.env` is in `.gitignore` and is never committed.
4. **Create the Admin account:**
   ```
   npm run seed:admin
   ```
5. **Start the server:**
   ```
   npm start
   ```
6. Open **http://127.0.0.1:3000** in your browser.

## AI Disclosure & Prompt Appendix

### Tools used
- **Claude (Anthropic)** generated the initial application code from the prompt below. I also used Claude as a guide for setup and debugging on Windows, for planning my QA tests, and for drafting this README. I ran every test myself and made the final decisions.

### Exact prompt used
```text
Act as a senior security engineer. Build a lightweight full-stack application (REST API with a simple HTML/JS frontend) demonstrating basic Authentication and Role-Based Access Control (RBAC).
Stack: Node.js, Express, SQLite (better-sqlite3), bcrypt, and JWT.
The application must include:

1. User registration and login with two roles: 'User' and 'Admin'.
2. Password hashing using a modern, secure algorithm.
3. Token-based (JWT) authentication.
4. Three distinct endpoints/views:
   * Public: accessible to anyone (home/landing page).
   * Protected (User): accessible to any authenticated user (profile/dashboard).
   * Restricted (Admin only): accessible ONLY to users with the 'Admin' role (user management list).

Provide the backend server code, route-guard middleware, and a minimal HTML/JS interface to test registration, login, logout, and role access.
```

### Security audit of the AI output
I reviewed the generated code against the assignment's Security Reality Check.

| Check | Result |
|---|---|
| Password storage | **Good.** bcrypt with cost factor 12. Verified in the database: every hash starts with `$2b$12$`. |
| Server-side enforcement | **Good.** The Admin check is `requireRole('Admin')` middleware on the API route, not just hidden buttons. A logged-in User gets `403` when calling the admin endpoint directly. |
| Token and secret safety | **Good.** `JWT_SECRET` comes from `.env`, and the server refuses to start if it is missing or under 32 characters. The JWT is stored in an `httpOnly`, `SameSite=Strict` cookie. Password hashes are never returned by any endpoint. |
| Error leakage | **Good.** Login returns the same generic message and status for an unknown username and a wrong password, and a dummy hash comparison keeps response times similar. A global error handler hides stack traces. |

### What the AI got right
- Parameterized queries only (no SQL string concatenation), so SQL injection input is treated as plain text.
- New registrations are always created as `User`. A `role` field sent in the request is ignored, so nobody can register themselves as an Admin. The Admin account is created by a server-side seed script.
- The user's role is read from the database on each request, not trusted from the token.
- `helmet` security headers, a 10 kb request body limit, and input validation on username and password length.
- The frontend uses `textContent` and never `innerHTML`, which avoids script injection through server data.

### What I found and patched
1. **No limit on login attempts (flaw in the AI code).** The login endpoint allowed unlimited password guesses. I added `express-rate-limit` so an IP is blocked for 15 minutes after 5 failed logins and receives `429 Too Many Requests`. Successful logins do not count toward the limit. See the commit "Add login rate limiting".
2. **Dependency problem on Windows (environment fix, not a security flaw).** The newest `better-sqlite3` needed a Visual Studio build and failed to install, so I pinned `better-sqlite3@12`, which ships a prebuilt Windows binary.

### Known gaps I did not fix
- The rate limiter is per IP and stored in memory, so it resets when the server restarts.
- JWTs cannot be revoked before they expire (1 hour), and there is no refresh token.
- No CSRF token. `SameSite=Strict` cookies are the only protection.
- Passwords are checked for length only, not for common-password lists.
- The local demo runs over plain HTTP. The cookie's `Secure` flag turns on when `NODE_ENV=production`, which requires HTTPS.
